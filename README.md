# Tim Langeveldt — Precog Security

Personal site and Precog Security landing page. Static HTML, CSS and JavaScript,
served straight off GitHub Pages: no build step, no server, no runtime
dependencies.

The code that actually belongs to this repository is small — a countdown plugin,
a rule-based chat bot, a campaign link builder and the page that ties them
together. Everything else is third-party, and is now pinned, checksummed and
isolated under [`vendor/`](vendor/manifest.json).

---

## Quick start

```bash
git clone https://github.com/tim777z/Tim.github.io.git
cd Tim.github.io
nvm use                 # optional; honours .nvmrc
npm ci                  # installs nothing: the site has zero runtime dependencies
npm run verify          # lint + secret scan + vendor integrity + tests
npm start               # http://127.0.0.1:8080/
```

`npm start` runs [`scripts/serve.mjs`](scripts/serve.mjs), a small static file
server written against the Node.js standard library. You can also just open
`index.html` in a browser; the site has no build output to generate.

**Requirements:** Node.js >= 20 (see `.nvmrc`). Nothing else.

## Commands

| Command | What it does |
| --- | --- |
| `npm start` | Serve the site on `http://127.0.0.1:8080/` (`-- --port 8081` to change) |
| `npm test` | Run the test suite (`node --test`, no test framework to install) |
| `npm run lint` | Syntax check plus the security and hygiene rules for first-party code |
| `npm run check:secrets` | Fail if a credential is committed |
| `npm run verify:vendor` | Fail if a vendored file does not match its SHA-256 pin |
| `npm run vendor:sync` | Re-materialise the pinned jQuery copy in `vendor/` |
| `npm run verify` | All of the above, in the order CI runs them |

### Third-party code

Everything third-party lives in `vendor/`, and `vendor/manifest.json` records
for each file its version, licence, source URL and SHA-256. `npm run verify:vendor`
fails on three things: a file that does not match its pin, a file with no pin, and
a manifest entry with no provenance.

jQuery is the one library that is worth explaining: it is declared in
`package.json` at an exact version, and `npm run vendor:sync` copies it out of
`node_modules` (re-checking the tarball integrity hash npm verified at install
time) into `vendor/jquery-<version>/`, then re-pins the manifest. So the file in
the repository can always be traced back to a lockfile-verified download.

To upgrade:

```bash
npm install jquery@3.7.1 --save-exact
npm run vendor:sync
npm run verify
```

### Third-party embeds

Three external services are used: Facebook (like/share), Google Programmable
Search, and Google Maps. Each is loaded from an `https://` URL, and the Maps SDK
is only requested after the visitor clicks the map button.

## How this is verified

`npm run verify` runs four gates, all of which CI runs on every push and pull
request:

1. **`npm run lint`** — `node --check` on every first-party script, plus rules for
   the things that actually matter in a browser: no plaintext `http://`
   subresource or redirect, no `innerHTML` sink, no `eval`/`new Function`/
   `document.write`, no duplicate element `id`. Rules are in
   [`scripts/lint.mjs`](scripts/lint.mjs) and are written against the standard
   library, so the gate works on a machine that has never seen this repository.
2. **`npm run check:secrets`** — scans first-party files for credentials
   (private keys, cloud and payment tokens, JWTs, `password = "..."` assignments).
   Anything genuinely public is declared, with a reason, in
   [`scripts/secret-scan-allowlist.json`](scripts/secret-scan-allowlist.json) and
   still reported as a warning so it never goes quiet.
3. **`npm run verify:vendor`** — the integrity check described above.
4. **`npm test`** — 60+ tests, see below.

### What the tests cover

The browser code has no build step, so the tests execute the real, shipped files
inside a `node:vm` context with a small jQuery double and a fake clock
([`test/harness.mjs`](test/harness.mjs)). The tests are pinned to behaviour that
used to be broken:

- `test/timer.test.js` — countdown formatting, completion, and the two shipped
  bugs: settings leaking between elements, and `stayVisible` throwing on a parent
  with no layout.
- `test/chat-bot.test.js` — every rule and reply, plus the `TypeError` on nullish
  input and the upper-case keywords that could never match.
- `test/tracking.test.js` — the tracking link builder: https only, parameter
  allowlist, encoding, and the injection attempts that the old string
  concatenation allowed.
- `test/site-assets.test.js` — every local `src`/`href` in every page resolves to
  a file that exists, one jQuery, no EOL jQuery, no plaintext subresources, no
  duplicate ids.
- `test/vendor-manifest.test.js` — the manifest matches the files on disk, and
  the removed end-of-life blobs have not come back.
- `test/serve.test.js` — the development server, including raw-socket path
  traversal attempts (a `fetch()` client normalises `..` away before it sends).

### Why there is no ESLint, Prettier or Jest

Every gate here is implemented with the Node.js standard library, so
`npm ci && npm run verify` works on a machine that has never seen this
repository, with no downloads, no install scripts and no third-party code
executing in CI. Adding a linter or a test framework would add a supply-chain
surface to a project whose whole point is that it has none. If the site grows
real application logic, revisit that trade-off deliberately and record it here.

## Security

Read [`SECURITY.md`](SECURITY.md). In short:

- The site is static. There is no server, no database, no session and no login.
- There is exactly one credential in the repository, a Google Maps *browser* API
  key, which is public by design and declared in the secret-scan allowlist. It
  must be restricted by HTTP referrer in the Google Cloud console.
- Nothing should ever be added under `.env`; `.gitignore` blocks it and
  `npm run check:secrets` fails the build if a key file appears.

Reporting a problem: open a GitHub issue, or email the address in the site
footer. Please do not open a public issue for an unfixed vulnerability.
